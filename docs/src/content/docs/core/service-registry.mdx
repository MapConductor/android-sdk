MapConductor provides a lightweight “plugin” mechanism called `MapServiceRegistry`.
It lets feature modules (like marker clustering/strategies) integrate with any provider module without requiring the provider’s `MapViewController` to implement feature-specific interfaces.

## How It Works (Android)

- The registry belongs to the map state: `MapViewState.serviceRegistry`.
- `MapViewBase` exposes it via the CompositionLocal `LocalMapServiceRegistry`.
- Feature modules resolve capabilities from the registry at runtime.

This keeps modules decoupled: provider modules “register” capabilities, and feature modules “use” them.

The state is the owner on every platform — `MapViewState.serviceRegistry` in the Android, iOS and
React SDKs alike — because the state is the one object whose lifetime matches the map instance and
which both the provider and non-Compose hosts (React Native, Cordova) can name.

## Marker Rendering Support

Marker clustering and strategy-based rendering need a provider-specific renderer/controller.
Providers expose that via:

- `MarkerRenderingSupport<ActualMarker>`
- `MarkerRenderingSupportKey` (registry key)

Built-in provider modules register `MarkerRenderingSupportKey` automatically, so `android-marker-clustering` works without any inheritance between controllers and feature interfaces.

## Custom Provider Integration (Android)

If you are implementing your own provider module, register `MarkerRenderingSupport` into
`state.serviceRegistry`. `MapViewBase` picks it up from the state — there is no registry parameter
to pass, and you should not create one with `remember { MutableMapServiceRegistry() }`.

```kotlin
// Register while the controller is created, before the map content is composed:
// MarkerClusterGroup returns early when the capability is missing, and the registry
// is not Compose state, so filling it later does not trigger recomposition.
state.serviceRegistry.put(MarkerRenderingSupportKey, myMarkerRenderingSupport)

MapViewBase(
  state = state,
  /* ... */
)
```

Because the state outlives the composable, take the capability back when the view goes away.
`MapViewBase` already does this for `MarkerRenderingSupportKey`:

```kotlin
DisposableEffect(state) {
  onDispose { state.serviceRegistry.remove(MarkerRenderingSupportKey) }
}
```

Use `remove()` rather than `clear()` so other capabilities registered on the same map survive.

Non-Compose hosts (React Native, Cordova) have no state object, so the
`create*ViewController(serviceRegistry = …)` functions still take a registry directly.

## iOS / SwiftUI Note

The iOS SDK has the same registry:

- `MapServiceKey` / `MapServiceRegistry` / `MutableMapServiceRegistry`
- `MarkerRenderingSupportKey`
- The registry lives on the state object, as `MapViewState.serviceRegistry` — same as Android.

Provider views register capabilities into the registry so feature modules can remain provider-agnostic.

It is *not* delivered through SwiftUI `Environment`. Map content is a `MapViewContent`
**value** assembled by `@MapViewContentBuilder`, so overlay items such as `MarkerClusterGroup`
are never placed in the view hierarchy and cannot read an `@Environment`. What they do share
with Compose is that the content closure runs *inside* the provider's `body`, so the provider
wraps that call in a main-actor dynamic scope, which gives the same visibility window as
`LocalMapServiceRegistry`:

```swift
let mapContent = MapServiceRegistryScope.with(state.serviceRegistry) { content() }
```

Add-on modules then read `MapServiceRegistryScope.current` while their content is being built.
